# Part 2 — Code reality

Everything in this part cites a file I read at this commit.

## 2.1 The cold mobile open, traced. CERTAIN on each step.

A recipient taps `pokemonvgcteamreport.com/s/ab12cd34` in Discord on 4G:

1. **Server**, `src/app/s/[id]/page.tsx` → `generateMetadata` runs **2 Neon queries** (`shares`,
   `collaborators`) + 1 Redis read (`getShareOgCard`).
2. **Server**, same file → the default export `SharePage` runs **the same 2 Neon queries again** for
   JSON-LD and the heading. No `React.cache()` anywhere in `src/app` (grep: zero hits), and
   `getDb()` mints a fresh `neon()` client per call, so nothing dedupes them. **4 Neon round trips
   where 2 would do**, on the one route whose own code comments blame "Neon cold start" for a 15s
   timeout budget.
3. **Server** returns `<JsonLd>` + `<ShareRedirectClient>`. `src/app/s/[id]/redirect.tsx` is 25
   lines: an `sr-only` `<h1>`, a spinner, the words "Loading shared team...", and
   `router.replace("/?s=<id>")`. **Not one byte of the team is in that HTML.**
4. **Client** downloads and hydrates the bundle, client-navigates to `/`, mounts `HomePageClient`
   (1,849 lines) and `useHomePage` (934 lines).
5. **Client** fetches `/api/share/<id>` — a **fifth** DB round trip (Redis-cached for public shares,
   and edge-cached `s-maxage=30`, so repeat views are cheaper; a first view is not).
6. `useShareUrl.ts` calls `history.replaceState(null, "", "/s/<id>")` to restore the clean URL.
7. Report renders.

**The recipient sees three different loading treatments in one open** (HIGH):
`src/app/s/[id]/loading.tsx` — an excellent 80-line skeleton with a team header, six sprite circles
and six stat-bar cards — flashes during the server await, is **thrown away** for the worse contentless
spinner in `redirect.tsx`, which is then replaced by a *third*, different skeleton at
`HomePageClient.tsx:841-880`. The product already owns the right loading UI twice over and shows the
wrong one at the moment that matters.

**Time-to-first-content is bounded below by a full bundle download plus a cold DB round trip.**
`useShareUrl.ts` sets the share-fetch abort at **15 seconds**, with the comment *"5s was too
aggressive for Neon cold start + edge miss on slow networks."* That number is the team's own estimate
of its worst case, and nothing of the team streams before it.

This is VGC-318. The architectural fix is large — `TeamReport.tsx` is `"use client"`, as are
`TeamOverview`, `PokemonDetailSlide` and the lazily-loaded charts — so a true server-rendered report
is a branch, not a night. **But a cheap 80% exists and nobody has taken it: see rec #1.**

## 2.2 The error state is wrong for every failure except the one it names. CERTAIN.

`useShareUrl.ts` collapses the fetch to `.then(r => r.ok ? r.json() : null)` and `.catch(() => settle(null))`.
`settle(null)` sets `decodeFailed`. `HomePageClient.tsx:824` then renders one screen for all of it:

> **Failed to load shared team**
> *The link may be corrupted or expired. Ask the creator for a new link.*
> `[ Build your own ]`

Everything below lands on that screen (CERTAIN on each cause, from `src/app/api/share/[id]/route.ts`):

| Real cause | What the recipient is told | Should say |
|---|---|---|
| **15s timeout** (slow venue 4G, Neon cold start) | "link may be corrupted" | "Still loading — **Retry**" |
| **Private report** → 404 at `route.ts:208-210` | "link may be corrupted" | "This report is private. Ask the creator to share it." |
| **Rate limited** → `apiGuard({rateLimit:{key:"share-get", max:60}})` | "link may be corrupted" | "Too many requests — retry in a moment" |
| **500 / DB down** → `route.ts` catch | "link may be corrupted" | "Something went wrong — **Retry**" |
| **Schema mismatch** → `parseFetchedShareState` returns null | "link may be corrupted" | correct, finally |
| Deleted / unknown id | real 404 page (`page.tsx` calls `notFound()`) — correct | — |

**There is no Retry anywhere.** The only button is `handleDecodeFailed` (`useHomePage.ts:810-814`),
which calls `reset()`, `clearStoredShare()` and then **`window.location.href = window.location.origin`** —
a full navigation that destroys the share context. A recipient whose fetch timed out once on a bad
connection is told the creator's link is broken and is then taken away from it. Their only recovery
is to go back to Discord and tap again.

**And we cannot see any of this happening** (CERTAIN): `report_viewed` fires at
`HomePageClient.tsx:655` **only after `isSharedView` is true**, i.e. only on success. There is no
`share_open_started` and no failure event. The top of the funnel — the single widest point — is
**uninstrumented**, which is also why the October run could not size anything.

## 2.3 The first unfurl — the most important one — is a race the code can lose. HIGH.

This is new, it is the sharpest thing I found, and it is **not** the forbidden change.

- `src/app/api/share/route.ts:577` (create path) calls `schedulePublishShareOgImage(...)`, which wraps
  `publishShareOgImage` in `after()` — Next's "run after the response is sent".
- `useShareUrl.copyShareUrl` writes the URL to the clipboard **as soon as the POST responds**.
- The render it is waiting on is `renderTeamGraphic(data, "wide")`: a satori `ImageResponse` that
  fetches **six sprites** from `play.pokemonshowdown.com` (`team-graphic-image.tsx:449`), then
  `put()`s a PNG to Vercel Blob, then writes the Redis key.

So the sequence a creator actually performs — *click Share → link on clipboard → paste into Discord* —
takes a couple of seconds. The card render also takes a couple of seconds, starting later. **If
Discord's unfurler fetches `/s/<id>` before the Redis key lands, `getShareOgCard` returns `null`,
`generateMetadata` emits `images: []` and `twitter.card: "summary"`, and Discord caches that
text-only embed against the page URL.** The `?v=<fp>` cache-buster only changes the *image* URL; it
cannot force a re-unfurl of a page URL Discord has already cached. The first paste is the one that
spreads, and it is the one most likely to miss.

**The same gap exists for every report created before the feature shipped.** `scheduleOgImageBackfill`
also runs in `after()`, so the *first* crawler to hit an old `/s/<id>` renders the card but gets the
text embed itself; only the *second* visitor benefits — and crawlers do not come back.

**A second, slower leak:** `OG_TTL_SECONDS = 90 days` on the Redis key, with no refresh on read. A
link sitting in a six-month-old Discord thread or a Victory Road post silently reverts to a text
embed once the key expires, even though the Blob object still exists. Given §1.3 — an audience
already trained that previews rot — this is the wrong default.

All three are small, local fixes in two files. **None of them re-enables on-demand OG rendering on
`/s/<id>`; the card stays a pre-rendered static Blob URL, exactly as VGC-318 requires.** See rec #3.

## 2.4 The copy-link flow, and an iOS Safari hazard. CERTAIN on the code; MEDIUM on the platform behaviour.

`useShareUrl.copyShareUrl` does: POST `/api/share` → `await` → **then**
`await navigator.clipboard.writeText(publicUrl)`.

WebKit requires a clipboard write to occur in the same user-gesture task. After an awaited network
round trip the gesture has expired, and Safari can reject `writeText` with `NotAllowedError`. Our
catch then sets `shareStatus = "error"`, which `useShareFlow.shareButtonText` renders as **`t.failed`** —
so an iOS creator whose report **saved successfully** can see the Share button say "Failed".

Mitigations already in place (CERTAIN): the report *was* saved, `lastShareResult` is set, and
`HomePageClient` opens `ShareModal` on share completion, where the URL is displayed and
`handleCopyLink` offers a **fresh-gesture** copy that will succeed. So this is a wrong-label problem
rather than a lost-work problem — but "Failed" on a successful publish is the worst possible copy for
the product's primary action.

I could not test a real device (no network, no browser). **MEDIUM**, and worth one real-iPhone check
before anyone writes code. The clean fix is to distinguish "saved but not copied" from "save failed"
in `shareStatus`, not to restructure the flow.

**The rest of the modal is good** (CERTAIN) and should be left alone: separate copy actions for link,
Discord-formatted message, Showdown paste, rental code and embed iframe; each with its own 2s
confirmation, a `setCopyAnnouncement` live region for screen readers, a PostHog event, and a catch
that no-ops with a comment explaining the URL is visible and selectable anyway. Achievement-led
share text (`achievementHeadline`, `twitterText`, `redditText`, `discordText`) is already implemented —
R5's "W2 achievement-led share text" recommendation is **done**.

## 2.6 Smaller findings

- **No deep links into a report.** Grep for `slide=` / `#slide` across `useSlideNavigation.ts`,
  `useSlideSystem.ts` and `HomePageClient.tsx`: **zero hits**. A creator cannot link to "my
  Incineroar's spread" or "the speed tiers" — only to the top. Every good sharing product has
  per-section anchors (Part 3). Medium build; real creator value.
- **No QR of the share link.** `qrcode` is already a dependency and already dynamically imported in
  `TeamOverview.tsx:402` and `OTSSheetModal.tsx` — but only ever to encode the **rental code**. A QR
  of the `/s/<id>` URL in the share modal would be ~15 lines and is the right artifact for the two
  places this product lives: a venue table, and a stream overlay.
- **`TeamOverview.copyRentalCode` (line 410) has no `.catch`** — the only clipboard call in the
  codebase without one. A rejected write is an unhandled promise rejection and the "✓ Copied" state
  never flips. One-line fix; every sibling has the catch and the explanatory comment.
- **`canNativeShare` is gated on `"share" in navigator`** (`ShareModal.tsx:113`) — correct for
  link sharing, but it is the wrong gate for file sharing, which needs `navigator.canShare({files})`.
- **`handleNativeShare` swallows every error** including real failures, same `catch {}` as a user
  cancel. Fine today; it will hide `AbortError`-vs-real-failure once files are added.
- **Private reports leak nothing** (CERTAIN, and good): `generateMetadata` returns a bare title +
  `noindex` for non-public/non-unlisted rows before touching `data`; `SharePage` skips JSON-LD;
  `/api/share/[id]` 404s outsiders. Collaborator `?key=` URLs force `noindex, nofollow` so a leaked
  edit token cannot reach a SERP snippet. Do not regress any of this in rec #1 — the server-rendered
  hero must sit **inside** the same visibility gate.

# Part 3 — How good sharing products do it, and what we are missing

The left column is **design knowledge, not measurement**: I could not reach Strava, Pinterest,

descriptions of them in `.swarm/r5-mobile-share-ux.md` §1. Treat the patterns as hypotheses with
strong priors. The right column is code I read.

| Pattern that converts | Why it works | Our state |
|---|---|---|
| **The destination's first paint IS the artifact.** A Strava activity opens on the map and the numbers; a Pinterest pin opens on the image; a Behance project opens on the hero shot. Server-rendered, then enhanced. | The recipient's decision ("is this worth my attention?") is made in the first second, and it is made *on content*, not on a spinner. | **MISSING.** `/s/<id>` first paint is a spinner and the word "Loading". ### #1 — Server-render a content hero on `/s/<id>` instead of a bare spinner — **implementable tonight: YES**

Not the VGC-318 refactor. `SharePage` **already has the row** — species, tournament, placement,
record, creator, summary — and currently spends it on JSON-LD and an `sr-only` h1. Pass that same
data into `ShareRedirectClient` and render what `embed/[id]/page.tsx` already renders: real `<h1>`,
placement badge, six HOME sprites with names, truncated summary. The redirect still fires underneath;
the hero fills the several seconds of bundle-download-plus-fetch that are currently blank, and gives
crawlers and LLM retrievers actual content on a route that already emits CreativeWork JSON-LD and a
canonical.

While in the file, wrap the share+collaborator query pair in `React.cache()` so `generateMetadata`
and `SharePage` share one result — **4 Neon round trips become 2** on the one route whose comments
blame Neon cold start for a 15s budget.

- **Files:** `src/app/s/[id]/page.tsx`, `src/app/s/[id]/redirect.tsx`. Copy markup from
  `src/app/embed/[id]/page.tsx`. Extend `src/app/s/[id]/__tests__/metadata.test.ts`.
- **Must not regress:** the private/unlisted gate. The hero renders **only** when
  `is_public || is_unlisted`, same condition as the existing `visibleForLd` check. A private report
  must still show nothing but the generic title.
- **Watch:** the hero is replaced when the client view mounts. Keep it visually continuous with
  `loading.tsx` so it reads as progressive loading, not a flash. Also consider simply deleting
  `redirect.tsx`'s spinner in favour of `loading.tsx`'s skeleton.
- **Confidence:** CERTAIN on the defect. HIGH that content-in-first-paint beats a spinner. **No
  behavioural data** — rec #2 is what makes the win measurable, so ship #2 first or alongside.

### #2 — Tell the recipient what actually went wrong, give them Retry, and instrument the failure — **implementable tonight: YES**

Split `decodeFailed` into a reason (`"timeout" | "notfound" | "ratelimited" | "server" | "invalid"`)

**without navigating away from the share**. Add `share_open_started` and `share_open_failed{reason}`
PostHog events so the top of the funnel stops being invisible.

Highest leverage per hour in this list: it is the difference between "the creator's link is broken"
and "tap again", on the device and connection where the timeout actually happens.

- **Confidence:** CERTAIN on every failure mode in the §2.2 table.

### #3 — Make the unfurl card exist before the link is pasted, and stop it expiring — **implementable tonight: YES (with care)**

Three small changes, two files. **None of these re-enables on-demand OG rendering on `/s/<id>`** —
the card remains a pre-rendered static Blob URL, which is what VGC-318 requires.

1. **On the create path only** (`route.ts:577`), `await publishShareOgImage(...)` instead of
   scheduling it. A first publish has no card by definition, and this is the one unfurl that decides
   whether the link spreads. Cost: ~1-2s on first publish only; updates keep `after()`.
   If that latency is unacceptable on Share, the alternative is a readiness poll in `ShareModal`
   ("preparing preview…" for up to ~2s) — more code, same effect.
2. **Sliding TTL:** refresh `OG_TTL_SECONDS` on every `getShareOgCard` hit. Actively-viewed links
   then never lose their card; only genuinely dormant ones degrade. ~3 lines.
3. **Backfill:** consider a bounded `Promise.race([render, 1500ms])` for the no-card case in
   `generateMetadata` so the *first* crawler to reach an old report gets the image, since crawlers do
   not return. **Measure before shipping this one** — it adds latency to a human's HTML on the exact
   route rec #1 is trying to speed up. Lowest priority of the three.
- **Files:** `src/app/api/share/route.ts` (line ~577 only), `src/lib/sharing/og-image.ts`.
- **Validate:** the comment history says this area has burned the team twice. Check a real link in
  Discord's and X's card validators from an unblocked network **before** believing any of it. I could
  not reach production (403 CONNECT).
- **Confidence:** HIGH on the race mechanism (code-derived). UNVERIFIED live.
