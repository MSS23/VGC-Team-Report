## Part 1 — Technical SEO defects in the current tree

Ordered by leverage. None of these are covered by an existing ticket.

### T1 — CRITICAL: every one of the ~5,000 sitemapped `/s/[id]` URLs serves a spinner, not the report

`src/app/s/[id]/page.tsx:148-232` renders `<ShareRedirectClient to={"/?s=" + id} />`.
`src/app/s/[id]/redirect.tsx:9-24` is `useEffect(() => router.replace(to))` over a loading
spinner and an `sr-only <h1>`.

The consequences compound:

1. `sitemap.ts:46-51` submits the top 5,000 public shares at priority 0.6. The HTML Google
   receives for each is a spinner + hidden `<h1>` + JSON-LD. That is textbook **thin content /
   soft-404** at 5,000-URL scale — a site-wide quality signal, not a per-page one.
2. After JS execution Google sees a client-side redirect, which it treats as a redirect and
   consolidates `/s/[id]` → `/?s=[id]`.
3. `/?s=[id]` is the homepage. `src/app/layout.tsx:85-87` asserts
   `alternates.canonical: "https://pokemonvgcteamreport.com"`, and `src/app/page.tsx` is
   `"use client"` with no `generateMetadata`. So **every share URL ultimately canonicalises to
   the root domain.** The team content is never eligible to rank on its own URL.
4. The `CreativeWork` JSON-LD at `s/[id]/page.tsx:196-231` (name, description, author,
   datePublished) describes content that is **not present in the served HTML** — a
   structured-data/page mismatch, which is a documented Google spam-policy trigger.
5. The careful title/description work at `s/[id]/page.tsx:52-99` and the `?key=` noindex fix
   (VGC-266-era) are all buying unfurl quality on a URL that cannot rank.

This single defect nullifies the majority of the site's indexable surface area. Every other
finding in this report is smaller than it by an order of magnitude.

**Fix shape:** server-render the report at `/s/[id]` (the data is already fetched twice in that
file — once in `generateMetadata`, once in the page body). R5's mobile audit
(`.swarm/r5-mobile-share-ux.md:354`, rec R1) independently reached the same conclusion from a
performance angle; it has never been framed as an indexation bug, which is why it has not been
prioritised. Interim mitigation if a full SSR port is too large: emit the report's species,
spreads and summary as static server HTML *behind* the spinner rather than an `sr-only` heading,
and set an explicit `alternates.canonical` on `/` variants.

### T4 — `/tournaments` emits two conflicting `SportsEvent` graphs, one with a wrong Worlds date

Two independent `SportsEventJsonLd` calls render on the same page:

- `src/app/tournaments/page.tsx:63` — `UPCOMING_TOURNAMENTS` (2 events), `url` pointing at
  `/tournaments` for both, and **no `eventStatus`**, so `JsonLd.tsx:112` defaults every entry to
  `https://schema.org/EventScheduled`.
- `src/app/tournaments/TournamentsContent.tsx:228-239` — `TOURNAMENTS` (6 events), different
  `url` per event (`/explore?q=…&searchType=tournament`), and a correct date-derived
  `EventScheduled`/`EventCompleted`.

Four separate problems:

1. **Wrong date on the biggest event of the year.** `page.tsx:47-50` declares
   `"2026 Pokemon World Championships"`, `startDate: "2026-08-14"`, *"held August 14-17"*.
   Worlds 2026 is **28–30 August 2026** at Moscone Center, San Francisco (Moscone, worlds.pokemon.com,
   Bulbapedia). Today is 17 Aug — the site is telling Google the tournament already finished,
   11 days before it starts, during the exact window when "Worlds 2026" search volume peaks.
2. **Past events marked `EventScheduled`.** Indianapolis (2026-05-29) is nearly three months
   past and is still asserted as scheduled. Google demotes/rejects Event rich results on this.
3. **Duplicate/conflicting nodes.** Two `SportsEvent` graphs on one URL with different `url`
   values and different `eventStatus` for overlapping events.
4. **`location` is a bare `Place` with only `name`** (`JsonLd.tsx:100-103`, `:120-123`) — no
   `address`, which Google's Event structured-data spec requires for physical events, and no
   `endDate` on any node.

`TOURNAMENTS` also stops at `2026-05-01` (Global Challenge 2026 I): no NAIC 2026, no Japan
Championships 2026, no Worlds 2026. See G2.

### T5 — VGC-273 confirmed: `fe70914` dropped `lastModified` from every static + champions entry

`git show fe70914 -- src/app/sitemap.ts` removes `lastModified: now` from all 11 static pages
**and** from the `getRegM*MegasWithSprites()` map — reverting `83d195a` ("§7.6: add lastModified
to champion sitemap pages") two weeks after it landed. Current `sitemap.ts:12-36` has no
`lastModified` on any static or champions entry; only the DB-derived `/s/[id]` and
`/creator/[name]` entries have one (`:48`, `:63`).

**Caveat that should change the fix.** The removed value was `new Date().toISOString()` and the
same commit added `export const revalidate = 3600`. Restoring it verbatim would republish a
`lastmod` on ~83 URLs that changes every hour and correlates with nothing — Google explicitly
discounts `lastmod` values it judges inaccurate, and it does so at *sitemap* granularity, which
would also poison the genuinely-accurate `lastmod` on the 5,000 share URLs. So: restore
`lastModified`, but source it from something real (build/commit timestamp for static routes;
for `/champions/[slug]`, the `MAX(updated_at)` of the shares that feed that mega's page, which
is already queried in `champions/[pokemon]/page.tsx`). A straight revert of `fe70914` is the
wrong fix.

**Concurrent development (noticed at write-up time).** Another agent in this run has an
uncommitted edit in the shared tree adding a 12-line comment to `sitemap.ts` that reaches the
same conclusion from the other direction and closes VGC-273 as *intentional / do-not-restore*,
citing the hourly-`revalidate` interaction. That resolution is defensible and I do not object to
it — but note it leaves the `/champions/[slug]` pages with no `lastModified` at all, even though
a genuine per-mega timestamp is cheaply derivable from the shares those pages already query.
Recommend the ticket close as "revert was correct" **plus** a small follow-up for real
mega-page timestamps, rather than closing the door on `lastModified` entirely.

### T6 — 7 shipped locales, zero hreflang, zero localized URLs

Six languages of finished translation work are invisible to every search engine. Pikalytics
by contrast ranks localized URLs today (`pikalytics.com/pokedex/gen9championsvgc2026regma?l=spa`,
`pikalytics.com/champions?l=chs` both surfaced in live SERPs). This is the largest
already-paid-for SEO asset on the site sitting at zero yield.

## Part 2 — Keyword gaps NOT covered by VGC-217 / 262 / 227 / 258

### What changed since May (this reframes everything below)

The May audit's competitive set was Pikalytics / PokePaste / VGCpastes / Trainer Hill /
Limitless. Since then an entire **Pokémon Champions tooling cottage industry** has appeared, and
it is winning the Champions SERPs outright. Live results for Champions/SP queries now return:
ChampDex (`champdex.com`), ChampionsMeta (`championsmeta.io`), ChampsDex (`champsdex.com`),
PikaChampions (`pikachampions.com`), Stratadex (`stratadex.net`), RotomLabs (`rotomlabs.net`),
PokeSynergy (`pokesynergy.app`), Pokebase, BattleWise AI, GenPKM, ChampCalc, PokéChampions Coach,
PokemonBuilder, Game8, Serebii — plus `op.gg` and Pikalytics both shipping dedicated Champions
calculators and Champions team builders.

Two consequences:

- **"Team builder" is lost.** A live search for *best VGC team builder 2026 pokemon champions*
  returns Pikalytics ×5, PokemonBuilder, PokeSynergy — and no VGC Team Report at any position.
  Chasing it is not winnable in this cycle.
- **"Team report" is still ours.** A live search for *how to share a VGC team report link with
  EV spreads* returns `pokemonvgcteamreport.com/faq` at **position 1**, and the AI answer is
  written almost verbatim from our FAQ copy. The category term "team report" has effectively no
  competitor. **Strategic read: defend and deepen "team report" / "share a team"; stop spending
  on "team builder" head terms.**

### G1 — "pokemon champions damage calculator" / "SP survival spread"

- **Target queries:** `pokemon champions damage calculator`, `champions SP survival spread`,
  `what SP do I need to survive [move]`, `pokemon champions calc reg m-b`.
- **Intent:** transactional-tool. Highest-volume Champions query cluster that exists, and the
  one every new entrant launched with.
- **Why it's a gap, and an honest one:** we already compute damage inside reports, but there is
  no tool URL — the functionality is trapped behind "paste a team first". Note this SERP is now
  *dense* (7+ dedicated calculators). We should not ship a generic calc.
- **Page shape that could win:** not a calculator — a **survival-spread solver keyed to the 66/32
  budget**: "give me the minimum SP that survives X". `src/lib/analysis/stat-calculator.ts`
  already has the exact-arithmetic budget/trim machinery (`championsSpToEv`, the
  largest-remainder trim) that generic calc ports do not. URL `/tools/sp-survival` sitting beside
  the existing `/tools/ev-to-sp`, `SoftwareApplication` + `HowTo` JSON-LD, shareable result URLs
  (which feed T1's fix, since each solved spread is a linkable page).

### G2 — Worlds 2026 (event window is open **right now**)

- **Target queries:** `worlds 2026 vgc teams`, `pokemon world championships 2026 top cut`,
  `worlds 2026 winning team`, `[player] worlds 2026 team`.
- **Intent:** informational, extremely time-boxed — 28–30 Aug 2026, San Francisco. Volume peaks
  in the ~10 days before and the ~14 days after, then decays permanently.
- **Why it's a gap:** Pikalytics already has `pikalytics.com/worlds-2026` live and indexed.
  Bulbagarden owns the per-event results threads. Our `/tournaments` page's newest entry is
  `2026-05-01`, and our only Worlds structured data has the **wrong dates** (T4).
- **Page shape:** `/tournaments/worlds-2026` — a static route with correct `SportsEvent`
  (`startDate 2026-08-28`, `endDate 2026-08-30`, `Place` with `address`), a server-rendered list
  of public reports tagged to the event, and an `ItemList` of them. This is the one item in this
  report with a hard deadline: it is worth less every day after 30 Aug. It also cannot work at
  all until T1 is fixed, since the reports it links to are currently spinners.

### G3 — Reg M-A → M-B migration ("is X legal in Reg M-B")

- **Target queries:** `regulation m-b legal pokemon`, `what changed in regulation m-b`,
  `is [species] legal in reg m-b`, `reg m-a vs m-b differences`, `reg m-b mega list`.
- **Intent:** informational + verification. Every format rotation produces a durable spike, and
  M-B is current, so this is live demand now.
- **Why it's a gap and why it's *ours*:** `src/lib/validation/champions-legality.ts` is a real
  legality engine (dex, restricted ≤2, item/species clauses, SP/EV budgets). Game8 and Serebii
  publish static roster lists; nobody publishes an **interactive "paste your team, get a legality
  verdict"**. That is a genuinely defensible differentiator, unlike another calculator.
- **Page shape:** `/tools/reg-m-b-legality` — paste box → per-Pokémon verdict with the specific
  rule cited; below the fold, the full M-B legal Mega list rendered as server HTML (feeds the
  "reg m-b mega list" query too) plus an M-A→M-B diff table generated from
  `CHAMPIONS_REG_MB_ONLY_MEGAS`. `HowTo` + `FAQPage` JSON-LD. Zero manual upkeep — it renders
  from the same constants the app validates against.

### G4 — the six dormant locales (see T6)

- **Target queries:** `equipo VGC pokemon champions`, `ポケモン チャンピオンズ 構築`,
  `寶可夢 冠軍賽 隊伍`, and the `share/report` long tails in each.

### G5 — "[Mega] counters" / "how to beat [Mega]" — extends the existing pages, distinct from VGC-217

VGC-217 covers per-*species* EV-spread landing pages. This is a different intent on the *existing*

`mega kangaskhan counters`, `what beats mega metagross`). The May metadata draft
(`.swarm/drafts/r6-metadata-changes.md` §2) sketched a type-chart-derived counters FAQ item and
it was never shipped. Cheapest real content win in this report: one extra grounded FAQ entry per
mega page × 72 pages, no new routes. Keep it type-chart-derived — do not name specific counter
Pokémon that we cannot ground in data.

### G6 — "pokepaste alternative" / "how to share a pokemon team"

- **Target queries:** `pokepaste alternative`, `share pokemon team link`,
  `pokepaste vs vgc team report`, `better than pokepaste`.
- **Intent:** commercial-comparison — highest conversion intent in the whole set.
- **Why it's a gap:** we already rank #1 for the *how-to* phrasing via `/faq`, and

## Part 3 — AEO/GEO: would `llms.txt` actually get us cited?

### Method

Assessed the three named queries against what an AI crawler receives from
`public/llms.txt` (35 lines) + `public/llms-full.txt` (123 lines), cross-checked against what
the live SERP/AI answers currently say.

### Query-by-query

**"best VGC team builder"** — ❌ **Would not be cited, and should not be targeted.** `llms.txt`
opens by calling the site "the premier team report builder and sharing platform". An LLM
resolving "best team builder" has Pikalytics, PokeSynergy and PokemonBuilder all self-describing
as team *builders* with usage data; our unsupported "premier" superlative is the weakest kind of
claim (self-assertion, no third-party corroboration) and reads as marketing, which citation
models discount. Verified live: we appear nowhere for this query.

**"how to share a VGC team"** — ✅ **Already cited, and the strongest asset on the site.** Live
search returns `/faq` at position 1 with the AI answer paraphrasing our copy. `llms-full.txt:77-84`
carries a clean numbered procedure. This works because the answer is *procedural and specific*
rather than superlative. One defect: step 5 and the closing line claim `/s/[id]` links "automatically
generate a rich Open Graph preview showing the team's Pokémon" — `s/[id]/page.tsx:104-118`
deliberately sets `images: []` because OG rendering was tried twice and produced broken unfurls.
We are advertising a feature we removed on purpose.

**"what is SP in Pokémon Champions"** — ❌ **Actively harmful in its current state.** Two problems:

1. `llms-full.txt:87-93` still teaches `1 SP = 1 EV` / "Standard Points" (T2). A crawler fetching
   both files gets a contradiction and will drop us for whichever source is internally consistent.
2. Even the *corrected* `llms.txt:29` is an outlier. It states "the first SP in a stat costs 4 EVs
   and every SP after that costs 8 (so 32 SP = 248+ EVs)". Every other source in the live SERP
   (ChampDex, Game8, RotomLabs, BattleWise, ChampsDex) states **1 SP = 8 EVs, 32 SP = 256 EVs,
   66 SP ≈ 528 EVs**. Reading `src/lib/analysis/stat-calculator.ts:84-116`, our 4-then-8 ladder is
   the *importer's* rounding rule — `evToChampionsSp` is `ceil(ev/8)` with a floor of 1 so the
   conventional 4-EV chip doesn't vanish — not a claim about the game's economy. We are stating an
   implementation detail as a rule of the format, in the one file designed to be ingested as
   authoritative fact. Consensus-checking LLMs will treat us as the wrong source.
   *(Flagging as a citation/consistency risk. Which figure is right in-game should be verified
   against a primary source before any copy change ships; the report deliberately does not rule on it.)*

### Structural problems with both files

- **Stale on the current regulation.** Both are dated `2026-05-23`, describe Champions as
  "Regulation M-A", and `llms-full.txt:64` calls M-A "the 2026 format". M-B is current. Same
  defect class as T3.
- **Factually wrong example.** `llms-full.txt:72` cites "Mega Salamence's Aerilate" as an
  enabled Champions combination. `grep salamence src/lib/data/mega-pokemon.ts` → **0 hits**;
  Salamence is not in the 75-entry Champions Mega list. We are hallucinating in our own
  ground-truth file.
- **Missing surfaces.** Neither file mentions `/tools/ev-to-sp` (VGC-262, shipped), `/compare`,
  `/support`, or the 7-language support. `llms.txt` lists 7 URLs; the sitemap has ~83 static ones.
- **No answerable atoms.** The files are prose *about* the product. There is not one embedded
  concrete artefact an LLM can lift — no worked EV→SP conversion example, no sample report URL,
  no numbers table. Citation models strongly prefer sources with liftable specifics.
- **No `llms.txt` → `llms-full.txt` pointer.** The llmstxt.org convention is for the short file
  to link the detail file; ours does not, so a crawler that reads only `llms.txt` never learns
  the deep file exists.

### Concrete improvements (content only — drafted copy in the drafts file)

1. **Fix `llms-full.txt:87-93` first.** Nothing else in this section matters while the site
   serves a corrected short answer and an uncorrected long one. Extend
   `sp-docs-drift.test.ts` to read `llms-full.txt` so the guard covers the file that has the bug.
