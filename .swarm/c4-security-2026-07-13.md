## 3. API route sweep (54 route files)

### 3.1 🟠 **HIGH — Team-graphic route serves private reports**
**File:** `src/app/api/team-graphic/route.tsx:96`
```ts
const rows = await sql`SELECT data FROM shares WHERE id = ${shareId} AND deleted_at IS NULL`;
```
No `is_public` / `is_unlisted` / owner check. A caller who knows a share ID (8 alphanumeric — high entropy, but shared in URLs) can generate a PNG that reveals: team composition (six species + items + types), tournament name, placement, record, creator name, tags. The main `/api/share/[id]` handler explicitly enforces "private → 404" for outsiders (line 269), and `/api/oembed` gates on `is_public = TRUE`, but this route quietly bypasses both. Also doesn't validate `shareId` shape (no IdSchema).

**Fix (<10 lines):**
```ts
const rows = await sql`
  SELECT data FROM shares
  WHERE id = ${shareId} AND deleted_at IS NULL
    AND (is_public = TRUE OR is_unlisted = TRUE)
`;
```
Also apply `IdSchema` (the `/^[A-Za-z0-9]{8}$/` regex used elsewhere) to `shareId`.

### 3.2 🟡 **MEDIUM — `avatarUrl` accepts any HTTPS host**
**Files:** `src/app/api/user/profile/route.ts:21-24` and `src/components/social/CreatorProfile.tsx:113`

Zod only checks `v.startsWith("https://")`. Any user-set URL then renders as `<img src>` on public creator pages, leaking Referer to arbitrary origins and enabling third-party tracking pixels or IP-logging services on every viewer of the profile. Not XSS (no HTML injection), but a privacy issue on a public page.

**Fix (<15 lines):** Allowlist trusted CDN hosts in the zod refine:
```ts
const ALLOWED_AVATAR_HOSTS = new Set([
  "img.clerk.com", "images.clerk.dev",
  // add Cloudinary / any deliberate host here
]);
// in schema:
avatarUrl: z.string().max(500).optional().refine((v) => {
  if (!v) return true;
  try { return ALLOWED_AVATAR_HOSTS.has(new URL(v).hostname); }
  catch { return false; }
}, { message: "Avatar host not allowed" })
```

### 3.3 🟡 **MEDIUM — Two competing share-ID regexes**
`SHARE_ID_RE = /^[a-zA-Z0-9_-]{6,16}$/` is used by `/api/comments/[shareId]`, `/api/comments/[shareId]/[commentId]` (no shareId check at all there — see 3.5), `/api/reactions/[shareId]`, `/api/reactions` (batch), `/api/views/[shareId]`. Actual IDs are always 8 alphanumeric — validated by the strict `IdSchema` in `/api/share/[id]`, `/api/share/[id]/fork`, `/api/share/[id]/versions`, `/api/sync/[id]`, `/api/user/collections`.

Parameterized SQL makes this **not a SQL injection risk today**, and cross-referencing rows on invalid IDs is functionally harmless (they just don't match). But loose regexes accept `_` and `-`, allowing enumeration of formats that don't exist and giving a wider attack surface should any future route interpolate this into anything other than a `${}` bind. Consolidate on the strict pattern.

**Fix (<20 lines):** Export `IdSchema` (or `SHARE_ID_RE = /^[A-Za-z0-9]{8}$/`) from one place and replace all six usages. Purely mechanical.

### 3.4 🟡 **MEDIUM — `/api/user/collections` DELETE action bypasses zod**
**File:** `src/app/api/user/collections/route.ts:149-155`
```ts
if (action === "delete") {
  const collectionId = raw.collectionId as string;
  if (!collectionId) return NextResponse.json({ error: "Missing collectionId" }, { status: 400 });
  await sql`DELETE FROM collections WHERE id = ${collectionId} AND user_id = ${userId}`;
```
Every other action (create/add-item/remove-item) uses zod schemas with `CollectionIdSchema`. The `delete` branch reads the raw `unknown` and casts. Parameterized SQL + `user_id = ${userId}` scope keeps this safe from injection/IDOR, but it's the one hole in an otherwise-clean file and inconsistent with the pattern.

**Fix (<10 lines):** Add `const DeleteBody = z.object({ collectionId: CollectionIdSchema });` and `.safeParse(raw)` in that branch.

### 3.5 🟡 **MEDIUM — Comment DELETE route lacks share-ID validation**
**File:** `src/app/api/comments/[shareId]/[commentId]/route.ts` — no `SHARE_ID_RE.test(shareId)` guard; only `commentId` is `parseInt`-checked. Parameterized SQL makes this non-exploitable, but the sibling GET/POST for the same resource *do* validate the shareId (`route.ts:26,86`). Add the guard for consistency.

### 3.6 ⚪ **LOW — `/api/pokepaste` POST is public**
**File:** `src/app/api/pokepaste/route.ts:114`. Unauthenticated, rate-limited at 20/min per IP. Forwards up to 50k chars of user content to `pokepast.es/create` from our server IP. Effectively a paste-through proxy — could be used for spam laundering or to trip pokepast.es rate limits from our IP. Consider requiring auth for POST (leave GET public) — or leave as-is; risk is low and pokepast.es owns their abuse response.

### 3.7 ⚪ **LOW — `/api/oembed` shareId regex allows non-8 IDs**
**File:** `src/app/api/oembed/route.ts:15` — `/\/s\/([A-Za-z0-9]{6,12})/`. Same theme as 3.3. Non-exploitable; tighten to `{8}` for hygiene.

### 3.8 ⚪ **LOW — In-memory presence Map grows across `/api/sync` invocations**
**File:** `src/app/api/sync/[id]/route.ts:11`. Module-scope `presence` Map + a `setInterval(…, 60_000)` scheduled at module load. On a serverless instance that stays warm, this leaks entries for every shareId ever synced by a client whose disconnect handler didn't run cleanly. Not a security risk, but a DoS-via-slow-leak on a single warm Lambda. Not fixable in <30 lines cleanly — defer.

## 4. CSRF / state-change protection

**File:** `src/middleware.ts:104-141` + `src/lib/security/csrf.ts` + `src/lib/security/cors.ts`.

Structure is solid:
1. **CORS** blocks any `Origin` header not in the allowlist (`isAllowedOrigin`) before the request even reaches the handler (`middleware.ts:115`). Exceptions: `/api/discord` (Ed25519 sig), `/api/webhooks/*` (HMAC/svix), `/api/builder/*`, `/api/setup` (bearer). All exceptions carry their own signature verification.
2. **CSRF double-submit cookie** (`x-csrf-token` header vs `csrf_token` cookie) is enforced for state-changing methods where a browser `Origin` is present but somehow not in the allowlist — a belt-and-braces catch. Same-origin (Origin missing or matching) is trusted, which is the standard pattern for a CORS-gated fetch API.
3. Handlers only parse `application/json` bodies — HTML `<form>`s can't produce a valid JSON POST that will pass Zod, giving a third defence-in-depth layer.

**One caveat, LOW severity:** `isAllowedOrigin` returns `true` when the Origin header is *absent* (`cors.ts:40`). A same-origin fetch has no Origin in some browser modes, so this can't be tightened without breaking things — but any non-browser client (server-to-server, curl, mobile app) that omits Origin also passes. Combined with bot-detection blocking `curl/wget/python-requests` etc. in `middleware.ts:68`, this is well-mitigated for browser attacks. Nothing to fix.

## 5. PII leakage in error responses

Grepped every `console.error` / catch handler in `src/app/api/**` (30+ hits). Every route responds with a **generic** `{ error: "Failed" }` / `{ error: "Failed to load share" }` / etc. Stack traces and DB error messages are logged to `console.error` but never returned in the response body. Zod validation errors return `parsed.error.flatten().fieldErrors` — which only exposes field names + generic messages ("Required", "Invalid input"), never row contents.

Comments GET *deliberately* omits `session_id` from the response (VGC-issue fix — §2.1). No route returns `owner_id`, `edit_token`, `session_id`, or user emails except where the caller is proven to be the resource owner (e.g. `/api/share/[id]` returning `_editToken` to the owner). Clean.

The one place `sessionId` still appears in a response body is via `_forkedFrom` metadata and `_collaborators` names — both explicitly public data by design.

Nothing to fix.
