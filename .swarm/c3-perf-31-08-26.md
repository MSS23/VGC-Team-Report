Read-only audit. Branch `claude/loving-sagan-ib785e`, HEAD `70c4633`.

## 0. Methodology note (important)

**Next 16 + Turbopack no longer prints a First Load JS column.** The build table is now
only `Route (app) | Revalidate | Expire`. `grep -c "First Load JS" build.log` → `0`.
There is also no `app-build-manifest.json` in `.next/` any more, so the usual
manifest-based reconstruction does not work either.

The table below was therefore reconstructed by parsing the **prerendered HTML in
`.next/server/app/**/*.html`** for every `/_next/static/chunks/*.js` referenced as a
`<script src>`, `<link href>` preload, or an escaped preload in the flight payload,
then summing the on-disk byte size of each unique chunk (gzip = `zlib.gzipSync(level 9)`).
This is the real initial JS the browser fetches for a cold load of each route — the same
quantity the old "First Load JS" column reported.

Dynamic (`ƒ`) routes (`/s/[id]`, `/embed/[id]`, `/creator/[name]`, `/notifications`,
`/dashboard/notifications`, all `/api/*`) have no prerendered HTML and are not in the
table; their client graphs are covered by the static import tracing in §3.

## 5. Ticket verdicts

### VGC-257 — "dex-subset.json (330.3 kB) is eagerly bundled into the homepage" → **ALREADY FIXED**

Two independent proofs:
1. The built chunk carrying `dex-subset.json` (`2s786ain9e09t.js`) is referenced by
   `/compare` only, and does **not** appear in `/`'s 21 initial chunks.
2. `page.tsx` reaches the dex only through `dynamic()` boundaries; a committed
   regression test (`src/lib/__tests__/homepage-eager-imports.test.ts`) locks that in.

The "330.3 kB" figure is also obsolete twice over: the JSON was re-encoded to positional
arrays (`schemaVersion: 2`, `scripts/build-dex-subset.mjs`) and is now **129,858 bytes**
on disk / 131.1 kB as a chunk / **33.9 kB gzip**. Fixed by `415a281` + `6cec919`. Close it.

### VGC-271 — "Lazy-load the dex-subset fallback (chunk is smaller than claimed)" → **STILL VALID, but rescope**

The ticket's own premise is confirmed: the chunk is **33.9 kB gzip**, not 330.3 kB raw —
about 10× smaller than VGC-257 claimed. The homepage half is already done. What remains is
one eager chain on **`/compare` only**:

`compare/page.tsx:4 → CompareContent.tsx:6 → pokemon.ts:2 → pkmn-dex-fallback.ts:35 → dex-subset.ts:39 → dex-subset.json`

`/compare` is the single worst route (1205.7 kB raw / 344.1 kB gz) and this chain drags in
both `dex-subset.json` (33.9 kB gz) and `pokemon.ts` (38.1 kB gz) — **72 kB gz, 21% of the
route's gzipped payload**, to service a fallback most pastes never hit. Retarget the ticket
at `/compare` (and note `/dashboard` pays 10.6 kB gz for a `pokemon.ts` slice too).
Given it is 34 kB gz and off the critical route, this is P3-at-best.

### VGC-256 — "lazy-load zod out of the client bundle (223.9 kB raw / 50.4 kB gzip)" → **ALREADY FIXED**

`url-codec.ts:12-22` already routes every schema use through a cached dynamic
`import("./url-codec.schemas")`, with an explicit do-not-revert comment naming VGC-256.
The zod chunk `3fh60j1aq6y_9.js` is referenced by **0** prerendered routes. All other zod
importers are server API handlers. Close it. (The chunk has since grown to 272.0 kB raw /
64.4 kB gz — worth keeping the tripwire comment in place.)

### VGC-268 — "motion eager on 7 routes (37.8 kB gz) and move-names eager on /" → **PARTIALLY VALID** (split it)

- **motion half — STILL VALID, numbers confirmed.** `0y3cx1zi-ccxg.js` = 117.6 kB raw /
  **38.4 kB gz** (ticket said 37.8 kB gz — accurate), eager on exactly **7 route groups**:
  `/`, `/changelog`, `/dashboard`, `/dashboard/profile`, `/explore`, `/feedback`,
  `/champions/[pokemon]`. The `/` chain is `page.tsx:10 → PasteInput.tsx:6`. This is now the
  **largest remaining ticketed win on the homepage** and should be the priority of the five.
- **move-names half — ALREADY FIXED.** Both move-names chunks are referenced by 0
  prerendered routes; every importer sits behind a `dynamic()` boundary. Drop that half.

### VGC-269 — "No bundle-size visibility since Next 16 + Turbopack dropped the analyzer" → **STILL VALID**

Directly reproduced. On Next 16.3.0 the build table prints only
`Route (app) | Revalidate | Expire`; `grep -c "First Load JS" build.log` → **0**. There is
no `app-build-manifest.json` in `.next/` either, and `@next/bundle-analyzer` is not
installed (`node_modules/@next/` holds only `env`, `eslint-plugin-next`, `swc-*`), with no
`ANALYZE` hook in `next.config.*` or `package.json`.

This is the meta-ticket and arguably the highest-leverage of the five: without it, every
one of the other four tickets required ~40 minutes of manual chunk archaeology to verify,
and three of the four carried numbers that were wrong or stale (330.3 kB → 33.9 kB gz;
223.9 kB → 272.0 kB raw; move-names already fixed but still ticketed).

**Suggested fix** — the reconstruction script used for this audit is small and works
against Turbopack output. Ship it as `scripts/bundle-report.mjs`: walk
`.next/server/app/**/*.html`, collect `/_next/static/chunks/*.js` from `src=`/`href=` and
escaped flight preloads, sum raw + gzip per route, print the table, and optionally fail CI
on a per-route gzip budget. That restores the lost column and would have made VGC-257/271
self-evidently stale.
