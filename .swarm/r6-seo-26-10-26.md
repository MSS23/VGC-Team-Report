### 2b. F4 — Homepage `FAQPage` markup for content that isn't on the page (HIGH, policy risk)

`src/components/home/HomePageServer.tsx` renders `<FAQPageJsonLd />` (the 5 `DEFAULT_FAQ_ITEMS` from `src/components/seo/JsonLd.tsx`) **outside** the Suspense boundary. The homepage body has no FAQ section at all — grepping `HomePageClient.tsx` for any of those five questions returns nothing, and the prerendered `index.html` contains the schema but no visible Q&A. Google's FAQPage policy requires the Q&A to be visible on the page; this is markup for absent content.

Compounding it: `"What is a VGC team report?"` is emitted **verbatim on both `/` and `/faq`** (`/faq` passes its own 13-item list, which includes that question). Two URLs claiming the same FAQ entity.

Two `HowTo` blocks also exist (`/` and `/faq`, different step sets). Google **retired HowTo rich results in Sept 2023**, so neither can produce a rich result today — they are inert payload, harmless but worth knowing before anyone invests in them.

Same caveat applies to the 81 mega pages: the comment in `src/app/champions/[pokemon]/page.tsx` says "Google surfaces these as rich snippets for long-tail queries", which has not been true for non-government/health sites since Aug 2023. The FAQ blocks there are still worth keeping — they are visible on-page (unlike the homepage's) and they are excellent LLM-extractable content — but not for the stated reason.

## 3. Sitemap + robots

### 3a. `src/app/sitemap.ts`

Static block: `/`, `/explore`, `/champions`, `/faq`, `/tools/ev-to-sp`, `/feedback`, `/tournaments`, `/changelog`, `/support`, `/privacy`, `/terms` + 81 `/champions/<slug>`. Dynamic: up to 5 000 `/s/<id>` (`is_public = TRUE AND deleted_at IS NULL`) and up to 5 000 `/creator/<name>` (grouped on `data->>'creatorName'`), with `lastModified`. `revalidate = 3600`; DB failure falls back to the static block inside a `try/catch`. All sound.

**Coverage: complete.** Every indexable route is present. No indexable route is missing.

### 3b. noindex-vs-sitemap self-contradiction — **verified still fixed** ✅

The v5.27 fix held. `/compare` sets `robots: { index: false, follow: true }` in `src/app/compare/page.tsx`, is **not** in `sitemap.ts`, and carries a load-bearing comment citing VGC-272 telling future editors not to re-add it. Confirmed against the build: `.next/server/app/compare.html` carries `<meta name="robots" content="noindex, follow">`.

I checked every other sitemapped URL for the same class of bug and found **none**:

- `/feedback`, `/changelog`, `/support`, `/privacy`, `/terms` — prerendered HTML has **no** robots meta (= indexable). Consistent.
- `/s/<id>`: sitemap selects `is_public = TRUE`; `generateMetadata` noindexes exactly when `!isPublic || hasEditKey`. Consistent. (The `?key=` noindex is a good catch — it stops a leaked collaborator edit token being cached in a SERP snippet — and `?key=` URLs are never sitemapped.)
- `/creator/<name>`: indexable, sitemapped. Consistent.
- Noindexed routes `/q/[id]`, `/embed/[id]`, `/dashboard*`, `/notifications` — none sitemapped. Consistent.

### 3c. `changeFrequency` / `priority` problems

Google has publicly ignored both fields for years, so this is cosmetic — but two entries are wrong on their own terms:

| URL | Declared | Reality | |
|---|---|---|---|
| `/tournaments` | `weekly`, 0.7 | Hardcoded array in `TournamentsContent.tsx`; unchanged since the May 2026 entry was added | **wrong** |
| `/changelog` | `monthly`, 0.3 | The most frequently updated page on the site (`changelog/data.ts` is 492 KB of prerendered HTML) | inverted |
| `/feedback` | `monthly`, 0.6 | A form page with no ranking intent, priority above `/tournaments`-class content | over-weighted |
| 81 `/champions/<slug>` | `weekly`, 0.8 | **No `lastModified` at all**, despite `revalidate = 3600` pulling fresh teams hourly | missed signal |

The real miss is the last row: the static block sets no `lastModified` on any entry, including the 81 SEO-critical pages. `lastModified` is the one field crawlers still act on.

### 3d. `public/robots.txt`

```
User-agent: *
Allow: /
Disallow: /api/
Sitemap: https://pokemonvgcteamreport.com/sitemap.xml
```

Correct, and the comment explains *why* it is a single group (a named `User-agent` group replaces `*` entirely, so the per-bot `Allow: /` groups that used to be here silently un-blocked `/api/` — the v5.27 fix). Nothing to change. Note `/compare`, `/q/`, `/embed/`, `/dashboard` are not disallowed here, which is the right call: they are `noindex`, and a `Disallow` would stop crawlers ever *reading* the noindex.

### 3e. Crawler gating in `src/proxy.ts` — **checked, clean** (one caveat)

`proxy.ts` runs `isBlockedBot(userAgent)` on **every page route**, so a mistake here would be an extinction-level SEO event. `src/lib/security/bot-detection.ts` checks the allow-list first and it covers `googlebot`, `bingbot`, `slurp`, `duckduckbot`, `applebot`, plus `gptbot`, `oai-searchbot`, `claudebot`, `anthropic-ai`, `perplexitybot`, `amazonbot` and the social unfurlers. `Google-InspectionTool`, `GoogleOther` and `AdsBot-Google` are not allow-listed but match no block pattern either, so they pass. **No search or AI crawler is blocked.**

Caveat, deliberate-looking but worth surfacing: `semrush`, `ahrefs`, `mj12bot`, `dotbot`, `blexbot` are blocked. That also blocks **your own** Ahrefs/Semrush Site Audit crawls, so nobody can run a third-party technical audit against prod. If the team ever wonders why Site Audit returns 403s across the board, this is why.

Also in `proxy.ts`: the canonical-host redirect fires for any host that is neither `pokemonvgcteamreport.com` nor `www.pokemonvgcteamreport.com` — so **`www` is never redirected to the apex**. Both hosts serve 200. Self-referencing canonicals point at the apex, so Google will consolidate, but a 301 `www` → apex is one line and removes the ambiguity.

### 3f. `public/llms.txt` — stale

Dated `Updated: 2026-05-23` (5 months old). Its "Main URLs" list omits **`/tools/ev-to-sp`**, which shipped in v5.26 (August 2026) and is one of only two genuinely unique tools on the site. Given the site explicitly allow-lists GPTBot/ClaudeBot/PerplexityBot/OAI-SearchBot, this file is doing real work and should list every tool route.

### F1 — the homepage is an empty shell

`src/components/home/HomePageServer.tsx` wraps `HomePageClient` in `<Suspense fallback={<p role="status">Loading team builder...</p>}>`. `HomePageClient` → `src/hooks/useHomePage.ts:64` calls `useSearchParams()`. On a statically prerendered route that forces the enclosing Suspense boundary to emit its **fallback** into the HTML. Confirmed: `index.html` is 38 959 bytes of `<head>` + JSON-LD + React Flight payload, containing the string `Loading team builder...`, **no `<h1>`, and not one internal link**.

So the site's strongest URL ships, to any non-JS client: a correct `<title>`, a correct canonical, 10 JSON-LD blocks — and no content and no links.

### F2 — the global navbar renders nothing, anywhere

`src/app/layout.tsx` renders `<Suspense fallback={null}><PersistentNavbar /></Suspense>`. `PersistentNavbar` calls `useSearchParams()` → same bailout, fallback `null`. Confirmed: the marker `aria-label="Mobile navigation"` appears in **0 of 95** prerendered files. The `NAV_LINKS` array in `PageNavbar.tsx` (`/`, `/explore`, `/champions`, `/compare`, `/changelog`, `/feedback`) contributes **zero** crawlable links sitewide.

Every internal link in the build therefore comes from `PageFooter` (`src/components/layout/PageFooter.tsx`) — and `HomePageServer` does not render `PageFooter`. The footer's own comment says `/champions` "was reachable only from the top nav, so the cluster had no sitewide footer link at all", which was exactly the right fix; the undiscovered half of that bug is that the top nav never rendered server-side in the first place.

### The actual HTML crawl graph

```
/  ──────────────────────────────────▶  (nothing)

any other page ──(PageFooter)──▶ /, /explore, /champions, /faq,
                                 /tools/ev-to-sp, /changelog,
                                 /support, /privacy, /terms, /feedback

/champions ─────▶ 81 × /champions/<slug>          (SSR, ChampionsContent — fine)
/champions/<slug> ─▶ 8 related megas + /champions  (rotating window — good)
```

- **`/champions` → 81 mega pages works properly.** `ChampionsContent.tsx` is a client component but uses no `useSearchParams`, so it SSRs fully: 95 links in `champions.html`, all 81 slugs present. The rotating `relatedMegas` window (offset by the current page's index rather than a fixed `.slice(0,8)`) is a genuinely good piece of internal-linking engineering — `mega-garchomp.html` links to 9 distinct siblings.
- **The cluster's only entrance is `/champions`**, reached only from `PageFooter`, which the homepage doesn't render. In HTML terms the 81 pages hang off a single hub with no homepage link.
- **Googlebot renders JS**, so in practice it will find the navbar on the second pass. **GPTBot, ClaudeBot, PerplexityBot and OAI-SearchBot do not execute JS** — and `bot-detection.ts` explicitly allow-lists all four. They are being served an empty homepage by design.

### F6 — `/tournaments` is an orphan

`grep -l 'href="/tournaments'` across all 95 prerendered pages returns **nothing**. It is in the sitemap at priority 0.7 and absent from `PageFooter`'s `NAV_LINKS` and from `PageNavbar`'s `NAV_LINKS`. Zero internal inbound links. One line in `PageFooter.tsx` fixes it.

### F3 — `/s/[id]` and `/creator/[name]`: the UGC corpus is not indexable

`src/app/s/[id]/page.tsx` renders `<ShareRedirectClient to={'/?s=<id>'} />` — a `useEffect` → `router.replace()` with a spinner and an `sr-only` `<h1>`. The report itself renders at `/?s=<id>`, which is the homepage route and therefore canonicals to `https://pokemonvgcteamreport.com`. Net effect for up to 5 000 sitemapped share URLs:

1. `<head>` is genuinely good — species-aware title, auto-composed description with placement/record hook, self-canonical, `CreativeWork` JSON-LD. Great for Discord/X unfurls, which is clearly what it was built for.
2. `<body>` has no team content for any crawler that doesn't run JS.
3. The URL that *does* have content tells Google it is a duplicate of `/`.

So the site's largest content asset — every public team report — is sitemapped, self-canonicalled, and effectively empty. **This is the structural ceiling on VGC-217 too:** per-species EV-spread pages will want to link out to real reports, and today there is nothing crawlable to link to.

`/creator/[name]` is better (real `generateMetadata`, ProfilePage + Breadcrumb schema) but `CreatorProfileWrapper` fetches client-side, so those pages also render no report links. And no prerendered page links to any `/s/` or `/creator/` URL at all.

One honest qualifier: `/champions/[pokemon]` **does** render `ReportCard` server-side from its DB query, and `ReportCard.tsx:164` emits `href={'/s/' + report.id}`. In production, with the DB reachable, the 81 mega pages *are* a real crawlable source of `/s/` links. They are absent from this build only because the container had no database. So in prod the picture is: `/s/` URLs have inbound links from mega pages, and then land on an empty shell. `/explore` contributes nothing either way, since its `ReportCard`s are client-fetched.

### Secondary note (not strictly SEO)

`next.config.ts` applies `X-Frame-Options: DENY` and CSP `frame-ancestors 'none'` to `/(.*)`, which includes `/embed/[id]`. The embed route and `/api/oembed` exist to be iframed on other sites — and embeds are a backlink channel. Those headers appear to block the feature outright. Worth a separate ticket; flagging here only because it touches off-site discovery. **Needs verification against prod response headers, which I could not reach.**

## 6. What is already done well

Worth recording so nobody "fixes" it:

- Self-referencing canonicals on every indexable route, with the root layout deliberately setting **no** site-wide canonical — and a comment explaining that the previous version made every page a declared duplicate of `/`.

- Mega-page FAQ answers are grounded in first-party data only, with an explicit comment refusing to invent "best spread" claims — the right call on structured-data spam risk.
- `relatedMegas` rotates its window so link equity spreads across all 81 pages.
- All 81 Reg M-C Megas now have sprites, so `ItemList` (81), `generateStaticParams` (81) and the sitemap (81) agree exactly. The "Coming Soon" branch in `ChampionsContent.tsx` is now dead code — benign, but it is dead.
