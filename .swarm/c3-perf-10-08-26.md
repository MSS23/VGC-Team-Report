### ⚠️ Methodology note — Turbopack prints no size table

**Next 16 + Turbopack does not emit the classic `First Load JS` / `Size` columns.** The route table it prints contains only `Route / Revalidate / Expire`. Every size number in this report was therefore derived, not read:

1. Parse each prerendered `.next/server/app/**/*.html` for `<script src="/_next/static/...">` references → that is the exact set of chunks a cold visitor downloads for that route.
2. Sum raw bytes and `gzip -9` bytes for each referenced chunk.
3. Identify chunk *contents* by byte-signature grep (`invalid_union`+`unrecognized_keys` ⇒ zod; `megaStone`+`Baxcalibur` ⇒ dex-subset; `jsPDF`, `html2canvas`, `posthog`, `clerk`, …).

Turbopack production builds **merge every module in a chunk into one scope-hoisted function**, so per-module attribution inside a chunk is impossible by parsing. That is why the two headline claims were validated by **differential builds** (§5) rather than by estimation — an estimate from `rolldown` tree-shaking was off by 4× for zod (see §5.1).

### 5.1 VGC-256 — zod in the client bundle: ✅ **CONFIRMED (understated)**

**Is zod in the client bundle?** Yes. Signature scan of all 80 emitted client chunks in the control build finds zod in exactly one:

```
=== ZOD-CONTAINING CHUNKS (vA) ===
0p-3laet_uvan.js   448.9 kB raw / 111.8 kB gzip   loaded by: /index
```

In vC (zod shimmed out) **no client chunk matches the zod signature at all** — clean removal, no straggler copy.

**Which client files import it?** No `"use client"` file imports zod *directly*. It arrives through one four-hop chain:

```
src/app/page.tsx                    ("use client", line 7)
  └─ import { useHomePage } from "@/hooks/useHomePage"
src/hooks/useHomePage.ts            (line 19)
  └─ import { useShareFlow } from "@/hooks/useShareFlow"
src/hooks/useShareFlow.ts           (line 4)
  └─ import { useShareUrl } from "@/hooks/useShareUrl"
src/hooks/useShareUrl.ts            ("use client", lines 6–9)
  └─ import { decodeShareState, type ShareableState } from "@/lib/sharing/url-codec"
src/lib/sharing/url-codec.ts        (line 1)
  └─ import { z } from "zod";          ← 264.9 kB raw / 62.8 kB gzip
```

The load-bearing edge is `useShareUrl.ts` importing the **value** `decodeShareState`. Every other importer of `url-codec` in client code is `import type` only and erases at compile time:

| Importer | Kind | Ships zod? |
|---|---|---|
| `src/hooks/useShareUrl.ts:9` | **value** (`decodeShareState`) | **YES** |
| `src/app/page.tsx:50` | `import type` | no |
| `src/hooks/useAutoDraft.ts:4` | `import type` | no |
| `src/hooks/useShareFlow.ts:7` | `import type` | no |
| `src/hooks/useCollaborativeSync.ts:4` | `import type` | no |
| `src/lib/utils/diff-state.ts:6` | `import type` | no |
| `src/lib/utils/version-diff.ts:1` | `import type` | no |
| `src/app/api/user/drafts/route.ts:7` | value (`ShareableStateSchema`) | server-only |

The other 23 zod importers are all `src/app/api/**/route.ts` server routes plus `src/lib/cache.ts` (`import type { ZodType }` — type-only). **None of them contribute to the client bundle.** `url-codec.ts` is the single client-side entry point for zod in the entire app.

**Realistic saving: −264.9 kB raw / −62.8 kB gzip on `/` only.** `/compare` is unaffected (0.0 kB) because `useShareUrl` is reached only via `useHomePage`.

**The ticket's 223.9 kB / 50.4 kB is an underestimate by ~18 % raw / ~25 % gzip.** Worth correcting on the ticket — this is a bigger win than it was sold as. (For calibration: a `rolldown`-based tree-shaken estimate put zod at only 64.4 kB raw / 17.2 kB gzip. Turbopack tree-shakes zod v4's barrel export **far** less aggressively than rolldown does — a 4× difference. Do not trust bundler-agnostic estimates for this dependency; measure with a real `next build`.)

#### Lowest-risk fix

`decodeShareState` is the only value crossing the boundary, and it is already only called in async/effect contexts inside `useShareUrl`. The minimal change:

1. In `src/lib/sharing/url-codec.ts`, move `import { z } from "zod"` and the schema definitions behind a lazily-initialised async getter:
   ```ts
   let schemasPromise: Promise<typeof import("./url-codec.schemas")> | null = null;
   const getSchemas = () => (schemasPromise ??= import("./url-codec.schemas"));
   ```
   i.e. split the `z.object(...)` definitions into a new sibling module `url-codec.schemas.ts` (the only file that imports `zod`), and have `url-codec.ts` `await import()` it.
2. Make `decodeShareState` `async` and `await getSchemas()` internally.
3. Update the single client call site in `src/hooks/useShareUrl.ts` to `await` it. It already runs inside a `useEffect`, so no render-path change.
4. `src/app/api/user/drafts/route.ts` imports `ShareableStateSchema` directly — point it at the new `url-codec.schemas` module so the server path keeps a static import and pays no dynamic-import cost.

**Risk: low.** One behavioural surface (`decodeShareState`) changes from sync to async, with exactly one client caller, already inside an effect. Keep `SerializedGamePlanSchema` / `SerializedMatchupPlanSchema` / `ShareableStateSchema` exported from the new module so server routes are untouched. **Existing tests to watch:** `src/lib/sharing/__tests__/url-codec.test.ts` and `src/hooks/__tests__/useShareFlow.test.ts`.

**Do not** try to fix this by swapping to `zod/mini` — that changes validation-error shapes and the `.strict()`-avoidance comment in `url-codec.ts` shows the decode path is deliberately lenient about legacy share links. Lazy-loading preserves semantics exactly; a library swap does not.

### 5.2 VGC-257 — `dex-subset.json` eagerly bundled into homepage: ✅ **CONFIRMED (understated)**

**Confirmed, and the ticket's own figure is exact.** Signature scan of the control build:

```
=== dex-subset-CONTAINING CHUNKS (vA) ===
0jy8.5bkrccrl.js   330.3 kB raw / 46.0 kB gzip   loaded by: /index
0-rxar2ioaec2.js   330.3 kB raw / 46.0 kB gzip   loaded by: /compare     ← second copy, not in the ticket
```

`330.3 kB` matches the ticket's number precisely. But **there are two copies** — the ticket only names the homepage. `/compare` carries an independent duplicate, so the true blast radius is **647.4 kB raw / 87.6 kB gzip of emitted JS**, not 330 kB.

**Exact import chains.** `src/app/page.tsx` is `"use client"` (line 1) and reaches the JSON by **two independent static chains**. Both must be fixed — cutting either one alone changes nothing:

```
CHAIN A (direct, one hop from the homepage)
src/app/page.tsx:61          import { detectMegaFromItem } from "@/lib/utils/mega-detect"
  └─ src/lib/utils/mega-detect.ts:3-6
       import { detectMegaFromItemDex, getMegaEntryFromDex } from "@/lib/data/pkmn-dex-fallback"
       └─ src/lib/data/pkmn-dex-fallback.ts:30
            import { ... } from "@/lib/data/dex-subset"
            └─ src/lib/data/dex-subset.ts:21
                 import rawSubset from "./dex-subset.json"    ← 331,481 bytes

CHAIN B (via the report tree)
src/app/page.tsx:11          import { TeamReport } from "@/components/report/TeamReport"
  └─ src/components/report/PokemonCard.tsx:27  (also TeamOverview, PokemonDetailSlide, SpeedTierChart,
     │                                          MatchupPlanSlide, CompareContent, useTeamReport)
     └─ import { lookupPokemon } from "@/lib/data/pokemon"
        └─ src/lib/data/pokemon.ts:2
             import { lookupPokemonFromDex } from "./pkmn-dex-fallback"
             └─ …same as Chain A → dex-subset.json
```

`/compare`'s copy comes from `src/components/compare/CompareContent.tsx:6` (`lookupPokemon`) and `:20` (`detectMegaFromItem`) — the same two chains.

**Is it dynamically loaded anywhere?** Partially, and that part is already correct. `src/components/report/InlinePokemonEditor.tsx:5` imports `allSpecies` from `dex-subset` and **is** properly lazy — `src/components/report/PokemonCard.tsx:15` wraps it in `dynamic(() => import("./InlinePokemonEditor"))`. That good work is defeated by chains A and B pulling the same JSON eagerly anyway.

**The critical detail that makes this fixable:** all three consumers use the subset **only as a last-resort fallback** after a static hand-maintained map misses.

```ts
// src/lib/data/pokemon.ts:3395-3403
      const collapsed = POKEMON_DATA[base];
      if (collapsed) return collapsed;
    }
  }
  // Dynamic fallback — anything not in our hand-maintained map …
  return lookupPokemonFromDex(species);        // ← only reached on a miss
```

```ts
// src/lib/utils/mega-detect.ts:31-33
  const entry = MEGA_STONE_MAP.get(item.toLowerCase());
  if (entry) { … return entry; }
  // Dynamic fallback — covers mega stones not yet in our static list.
  return detectMegaFromItemDex(item, species); // ← only reached on a miss
```

**330 kB is being paid up-front, on the app's busiest route, to service a cold path that a typical VGC team never touches.**

#### Lowest-risk fix

The three fallback entry points (`lookupPokemonFromDex`, `getMegaEntryFromDex`, `detectMegaFromItemDex`) are all **synchronous**, and their callers (`lookupPokemon`, `detectMegaFromItem`, `getMegaEntryFromSpecies`) are called during render in `PokemonCard` / `SpeedTierChart` / etc. Making them async is a wide, render-path-touching refactor. Two options, in increasing order of payoff:

**Option 1 — shrink the payload in place (lowest risk, ~58 % of the raw win, zero API change).**
`dex-subset.json` is 1,515 species stored as an array of objects, so every one of the seven field names is repeated 1,515 times. Re-emitting from `scripts/build-dex-subset.mjs` as a positional array-of-arrays plus a decode loop in `dex-subset.ts`:

| Shape | Raw | Gzip |
|---|---:|---:|
| current (array of objects) | 323.7 kB | 43.4 kB |
| array-of-arrays, same 1,515 species | **137.9 kB** | **34.1 kB** |
| array-of-arrays, minus `CAP`/`Custom` entries (99 species) | ~123 kB | ~30.5 kB |

Raw bytes are what dominate parse/eval time on mid-range mobile, and this is a pure serialisation change behind an unchanged public API — `getSpecies()`/`allSpecies()`/`getMegaStone()` keep their exact signatures. It needs no changes outside `scripts/build-dex-subset.mjs` and `src/lib/data/dex-subset.ts`.

> ⚠️ **Do not prune by `isNonstandard`.** It is tempting (`Past` = 454 entries, `Future` = 49, `CAP` = 80) but the 98 Mega species are split across `Past` (48) and **`Future` (49)** — the Champions-original Megas are the `Future` ones. Dropping `Future` would break exactly the feature this app exists for. Only `CAP` (80) and `Custom` (19) are safe to drop, and they are worth just ~14 kB raw.

**Option 2 — make the fallback truly lazy (full win, medium risk).**
Convert the subset to a module-level `let` populated by `await import("./dex-subset.json")`, fired once from a `useEffect` in `TeamReport`. Keep the three fallback functions synchronous but returning `null` until the subset resolves, and have the components re-render when it does. Every consumer already handles a `null` return from `lookupPokemon`/`detectMegaFromItem`, so the failure mode is "renders the static-map result now, upgrades a tick later" — not a crash. This recovers the full −323.7 kB raw / −43.7 kB gzip on `/` and the same again on `/compare`.

**Recommendation: ship Option 1 tonight, file Option 2 separately.** Option 1 is a build-script + accessor change with no render-path risk and captures most of the raw-byte win; Option 2 needs care around render-timing and deserves its own review. **Existing test to watch:** `src/lib/data/__tests__/champions-dex.test.ts` and `src/lib/data/__validate-mega-coverage.ts`.

## 8. Caveats

1. **Turbopack prints no size table.** Every number here is derived from emitted HTML + chunk bytes (§1). It is not directly comparable to a webpack-era `First Load JS` column, which excludes some runtime bytes. Numbers *are* internally consistent and reproducible — the control rebuild produced identical chunk hashes.
2. **Gzip, not brotli.** Vercel serves brotli; real transfer will be ~15–20 % below the gzip figures. Ratios and deltas hold.
3. **Concurrent swarm activity.** Other agents modified ~27 files under `src/` during this session and ran their own builds, clobbering `/home/user/VGC-Team-Report/.next` mid-analysis. **All §5 differential builds were therefore run from clean `git archive HEAD` trees in `/home/user/.perfvar/`, so they are uncontaminated**, and the control rebuild reproduced the original chunk hashes exactly.
   - `src/app/page.tsx` **was** subsequently edited by another agent (VGC-259, +12 lines adding an `sr-only` `<h1>`). Re-verified against the live working tree: it does **not** touch the import list — lines 7 / 11 / 61 (`useHomePage`, `TeamReport`, `mega-detect`), `url-codec.ts:1` (`import { z } from "zod"`) and `dex-subset.ts:21` (`import rawSubset from "./dex-subset.json"`) are all still present. **Both chains in §5 remain live on current `main`.**
   - Minor: the §4.2 transitive figures for `PokemonDetailSlide.tsx` and `TeamOverview.tsx` were measured close to the time those two files were edited by another agent; treat those two rows as ±small. All other rows are from untouched files.
4. **Source was not modified.** All patched trees were throwaway copies under `/home/user/.perfvar/`, deleted after measurement. `git status` in the repo shows only other agents' changes.
5. **Dynamic (`ƒ`) routes are unmeasured.** `/s/[id]`, `/embed/[id]`, `/creator/[name]`, `/notifications` produce no build-time HTML. `/s/[id]` in particular is a high-traffic share-link route and likely resembles `/` — worth a follow-up measurement against a running server.
