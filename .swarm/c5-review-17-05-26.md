## Issues Found

### 1. species column not written on UPDATE paths — MEDIUM

**File:** `src/app/api/share/route.ts`

The `extractSpecies()` function is called and the `species` column is written correctly on **new share INSERT** (line 330–337). However both UPDATE paths omit the column:

- **Edit-token update** (lines 215–226): the `UPDATE shares SET ...` does not include `species = ${parsedSpecies}::text[]`. If a user edits an existing report that was created before the migration, the column stays `NULL` forever.
- **Dedup update** (lines 299–310): same — the UPDATE that fires when an owner re-shares the same paste doesn't populate `species`.

The migration adds the column with `DEFAULT NULL` and a backfill index, so existing rows start at `NULL`. Without updating `species` on edit, the materialised column will be unreliable for any future O(1) meta query that tries to use it directly instead of falling back to the 6-CTE regex chain.

**Fix required before the column is used for meta queries:** add `species = ${parsedSpecies}::text[]` to both UPDATE statements (call `extractSpecies(state.paste)` before the updates).

### 3. extractSpecies() regex may false-positive on Nature line — LOW

**File:** `src/app/api/share/route.ts`, lines 46–66

The skip list checks `trimmed.startsWith('Nature')` but Showdown pastes have the format `Jolly Nature` — the word "Nature" appears at the end, not the start. The actual Nature line format (e.g. `Jolly Nature`) will **not** be skipped by this check and will be passed through the regex. The regex `^([A-Za-z][A-Za-z0-9 '-]+?)(?:\s*@.*)?$` will match `Jolly Nature` and attempt to push `"jolly-nature"` as a species name. The subsequent check `!name.includes('nature')` (lowercase) does catch this — but only because the name is lowercased first. It works, but the logic is fragile and the `startsWith('Nature')` check is a no-op.

No immediate bug, but worth cleaning up for correctness.

### 5. Linear webhook: JSON.parse before signature verification would expose parse errors — LOW

**File:** `src/app/api/webhooks/linear/route.ts`

The signature is verified on `rawBody` correctly. However `JSON.parse(rawBody)` on line 36 runs **after** a valid signature check, which is correct. If the body is not valid JSON (malformed webhook), the `JSON.parse` will throw and fall into the catch block which returns a 500. This is acceptable but ideally returns a 400. Not a security issue (signature is verified first), just a minor UX issue for debugging.
