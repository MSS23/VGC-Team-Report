## 0. Methodology (unchanged from 26-10-26 — re-verify before trusting numbers)

**Next 16 + Turbopack prints no size columns.** The emitted route table is `Route (app) | Revalidate | Expire` only (log lines 923–1021, reproduced verbatim in §1.1). Every KB figure below is **computed**:

- Union of each route's `.next/server/app/**/page_client-reference-manifest.js` → `clientModules[*].chunks` with `build-manifest.json`'s `rootMainFiles` + `polyfillFiles`, then each chunk read from disk and gzipped at level 9.
- The manifests are JS object literals assigned to `globalThis.__RSC_MANIFEST[...]`, not JSON — they are evaluated in a `node:vm` context, not regex-parsed.

**Polyfill caveat:** `0cz1d0mv5g_q7.js` (110.0 KB raw / 38.6 KB gz) ships with `noModule=""`, so modern browsers never fetch it. It is counted in "First Load JS" (Next's historical convention) and subtracted in the "modern gzip" column. **The modern column is the one real users pay.**

**Fingerprint caveat (important — three figures in last run's style of scan are false positives):** chunk→package attribution was done by grepping all 111 emitted chunks for payload fingerprints and then requiring *discriminating* strings. Single-species hits are placeholder copy, not data tables:

| Chunk | Routes | Single hit | Actual source — **not** the dex |
|---|---|---|---|
| `1mr_pjh4_hdy4.js` (floor, 23 routes) | all | `Flutter Mane` | i18n string: `commonLeadsPlaceholder: "…(e.g. Incineroar + Flutter Mane vs. most teams)."` |
| `0y_dltt9a0ntc.js` | `/explore` | `Flutter Mane` | `ExploreFilters` input placeholder `"e.g. Flutter Mane, Incineroar"` |

### 4.1 Lazy-load `effective-form` in `CompareContent`, and make the tripwire transitive — **81.0 KB gz**

- **Also:** add `components/compare/CompareContent.tsx` to `EAGER_HOMEPAGE_FILES` (rename to `EAGER_ENTRY_FILES`) **and** make the tripwire follow one hop of local re-export, or add `@/lib/utils/effective-form` + `@/lib/utils/speed-tier-form` to `FORBIDDEN_STATIC_IMPORTS`. ### 4.2 Move `CookieBanner` into `DeferredLayoutExtras` — **~12–14 KB gz × 23 routes**

- **Saved:** up to 17.9 KB gz off **every** route; realistically **12–14 KB gz**, because `3pzg3m6751lyb.js` also holds the `posthog-js/react` shim. Measure after.
- **Change:** `src/components/providers/CookieBanner.tsx` is mounted unconditionally at `src/app/layout.tsx:8` and does all its work in `useEffect` — it renders nothing synchronously. `src/components/ui/DeferredLayoutExtras.tsx` already exists for exactly this, with the comment *"None of these render anything above the fold — loading them after hydration keeps their code out of every route's initial bundle"*, and already defers `InstallPrompt`, `ConnectivityStatus`, `ServiceWorkerRegistration`, `ChunkErrorReloader`. `CookieBanner` was simply missed.
- **Files:** `src/components/ui/DeferredLayoutExtras.tsx` ⚠, `src/app/layout.tsx`.
- **Risk: low**, with one deliberate sign-off: the banner appears a beat later. Legally still fine (`PostHogProvider` gates on `notifyConsentChange`, so analytics cannot fire before consent) but it is a GDPR-adjacent surface and deserves an explicit decision, not a drive-by. The `open-cookie-settings` CustomEvent from `PageFooter` keeps working (listener registers later) — worth a Cypress assertion.

## 5. Render-cost problems in the report UI

### 5.1 `OffensiveCoverageChart` — zero memoisation, full recompute on every tap ⚠ **CONFLICT-RISK**

`src/components/report/OffensiveCoverageChart.tsx` (362 lines, **0** `useMemo`/`useCallback`).

```
152:  const [highlightedType, setHighlightedType] = useState<PokemonType | null>(null);
154:  const profiles = pokemon.map((mon, i) => { … resolveEffectiveTyping(…); getOffensiveProfile(…) });
172:  const teamSummary = ALL_TYPES.map((defType) => { … 18 × 6 scan … });
255:  onClick={() => { … setHighlightedType((prev) => (prev === type ? null : type)); }}
```

`profiles` and `teamSummary` are computed in the render body. Tapping any of the 18 type headers toggles `highlightedType` — which is **purely a highlight** — and re-runs the entire derivation: 6 × `resolveEffectiveTyping` (each → `lookupPokemon` + `resolveSpeedTierForm` → another `lookupPokemon`), 6 × up to 4 `lookupMove`, and ~432 `getEffectiveness` calls, then 108 more for the summary. **A highlight toggle invalidates the whole dataset.** Wrapping `profiles`/`teamSummary` in `useMemo` keyed on `[pokemon, speciesKeys, megaStates]` fixes it; `highlightedType` is then purely presentational.

### 5.2 `DefensiveCoverageChart` — same shape, same bug ⚠ **CONFLICT-RISK**

`src/components/report/DefensiveCoverageChart.tsx` (247 lines, **0** `useMemo`). Identical structure: `useState` at :44, `const profiles = pokemon.map(…)` at :46, `const teamSummary = ALL_TYPES.map(…)` at :62, `setHighlightedType` at :150. Same fix.

Both files are in `.swarm/main-changed-files.md`.

### 5.3 `TournamentMode` — unmemoised sort behind a view toggle ⚠ **CONFLICT-RISK**

`src/components/report/TournamentMode.tsx` (410 lines, **0** `useMemo`). `statView` is a `useState` (:223); the speed-tier derivation `.map(…).sort(…)` runs twice in the render body (:229, :340) and `translateMove` is called per move per render (:143, :184). N is 6, so the absolute cost is small — but it is free to fix and it is the same class of bug as §5.1.

`CalcInput.tsx` (384 lines) also has 0 memoisation; worth a look but no expensive derivation spotted.

### 5.4 Latent risk: `TeamStats` → `spread-builder` → `@smogon/calc` (117 KB gz)

`src/components/report/TeamStats.tsx` ⚠ is a 76-line presentational component that statically imports `displayStats` from `src/lib/analysis/spread-builder.ts` ⚠, whose **line 1** is `import { Generations, toID } from "@smogon/calc"` (plus `./damage-calculator`). Chunk evidence confirms this lands only in the lazy `295osw7xb5xjy.js` (501.5 KB / **117.0 KB gz**) today, so it is **not** a current finding. But a tiny stat table dragging the entire damage engine is fragile: the moment `TeamStats` (or `displayStats`) appears on an eager path, a route gains 117 KB gz. A `displayStats`-only module that does not reach `@smogon/calc` would de-fuse it.

### 5.5 Lists: no virtualisation anywhere, and one unbounded query

**Zero** virtualisation in the repo — no `react-window`, `react-virtual`, `react-virtuoso`, and no `IntersectionObserver` anywhere in `src/`.

- `/explore` is fine: `src/app/api/explore/route.ts:24` clamps `limit` to 12 (max 50) with cursor pagination.
- **`/dashboard` is not.** `src/app/api/user/reports/route.ts` has **no `LIMIT`** on the owner's reports query and selects the full `s.data` team blob per row (:28-31). `src/app/dashboard/DashboardContent.tsx` ⚠ then renders every returned report as a card, each mapping `report.species` to 6 sprites (:610, :775, :836), with no windowing and no "load more". A user with 200 saved reports downloads 200 full team payloads and mounts ~1,200 sprite nodes on one tab switch. This is a scaling cliff rather than a problem at today's volumes, but it is the one list that has no bound at either end. Fix is a `LIMIT`/cursor on the API plus incremental rendering — not virtualisation.

### 5.6 Micro: hoistable allocations

`SpeedTierChart.tsx` is otherwise well memoised (10 `useMemo`), but allocates a fresh `new Set()` as the "no modifiers" argument at :338, :349, :375, :379, :383 — inside `.map` callbacks. Hoist one module-level `const NO_MODIFIERS = new Set<string>()`. Also `maxDisplaySpeed` (:365) is an O(n) reduce outside `useMemo` and `positionChanges` does an O(n²) `findIndex` (:394) — both negligible at n≈30. Cosmetic only.
