`TeamReport` is a chain of early returns keyed on `currentSlide`; only the `currentSlide === 0` branch mounts `TeamOverview`, and `TeamOverview` owns the only `<h1>` in the whole viewer (`grep '<h1' src/components/report/` returns exactly `TeamOverview.tsx:418` and `:431`). Verified there is no compensating heading in the shell: `src/app/page.tsx` contains no `<h1>` at all, `src/app/layout.tsx` contains none, `Navbar`/`PersistentNavbar` contain none.

WCAG: **1.3.1 Info and Relationships (A)** and **2.4.6 Headings and Labels (AA)**; also 2.4.10 Section Headings (AAA) for the h3-first slides. Severity: **High** — it affects every viewer of every shared report, and heading-rotor navigation (the primary screen-reader way to orient on a new slide) is broken on 90 % of slides.

Mitigating fact worth knowing: slide changes *are* announced — `SlideNavControls.tsx:547-549` renders an `aria-live="polite"` sr-only "Slide 3 of 12: Flutter Mane". So the user is told where they are; what they cannot do is jump to or re-read the slide title by heading, and the document outline is malformed.

### The fix for VGC-259 — exact location and the visible/SR trade-off

**Recommended (single insertion point, one diff, cannot double up):** `src/app/page.tsx`, inside the slide region `<div role="region" …>` that opens at **line 1128** and whose children begin at **line 1142**. Insert as the first child of that div, before the `{tournamentMode ? … }` ternary:

```tsx
{(tournamentMode || physicalSlide !== 0) && (
  <h1 className="sr-only">
    {`${slideLabels[currentSlide] ?? "Team report"}${teamName ? ` — ${teamName}` : ""}`}
  </h1>
)}
```

Why here and not in the leaf components:

* `slideLabels` is already in scope at this level (`page.tsx:211`, built in `useSlideSystem.ts:54-63`: overview / "How to Pilot This Team" / each species name / "Team Analysis" / "Offensive" / "Defensive" / "vs. <opponent>" / "Matchups"), and it already feeds the region's `aria-label` at `page.tsx:1132` — so the h1 text and the region name stay in sync for free.
* The `physicalSlide !== 0` guard is what prevents a **second** h1 on slide 0, where `TeamOverview` legitimately owns the visible team-name h1 (`TeamOverview.tsx:431`) that is also the page's SEO h1. Use `physicalSlide` (not `currentSlide`) — that's the value passed to `<TeamReport currentSlide={physicalSlide}>` at `page.tsx:1215`, and creators can reorder/hide slides so the two indices diverge.
* The `tournamentMode ||` half covers `TournamentMode` (`page.tsx:1143`), which replaces the whole slide body and tops out at `<h3>` (`TournamentMode.tsx:280`).
* Putting it in `PokemonDetailSlide` instead would emit the heading **twice** into the DOM, because that component renders a mobile tree (`:919` `sm:hidden`) and a desktop tree (`:952` `hidden sm:grid`) and calls `renderHeroHeader()` in both. Only one is exposed (`display:none` prunes the other from the a11y tree), but it is fragile and has to be repeated in seven components.

**Visible vs. visually-hidden — the trade-off, stated plainly:** it must be **`sr-only`**. Slides 2..n and the analysis slides already render a *visible* title (`PokemonDetailSlide.tsx:582` species name, `SpeedTierChart.tsx:431` "Team Analysis", `MatchupSheet.tsx:67`, `MatchupPlanSlide.tsx:193`). A visible h1 would duplicate that text on screen and break the presentation-mode layout, which is tuned for one title per slide. The cost of `sr-only` is mild redundancy for screen-reader users (h1 "Flutter Mane — Rain Offense", then h2 "Flutter Mane"). That is the correct trade: WCAG asks for a programmatic outline, not visible chrome.

**If the implementer prefers zero SR redundancy**, the alternative is to promote the existing visible slide title from `h2` to `h1` in the four components that have one (`PokemonDetailSlide.tsx:582`, `SpeedTierChart.tsx:431`, `MatchupSheet.tsx:67`, `MatchupPlanSlide.tsx:193`) and add an `sr-only` h1 only to the three that start at h3 (`CommonModesSlide.tsx:181`, `OffensiveCoverageChart.tsx:168`, `DefensiveCoverageChart.tsx:72`) plus `TournamentMode.tsx:280`. Visually this is a no-op (Tailwind's reset means the tag carries no styling). It is 8 files instead of 1 and re-opens the double-h1 risk on slide 0, so I recommend it only if the team dislikes redundant announcements.

**Optional follow-up either way (fixes the level *skips*, 2.4.10):** with an h1 present, `CommonModesSlide.tsx:181`, `OffensiveCoverageChart.tsx:168` and `DefensiveCoverageChart.tsx:72` should become `<h2>`, and `CommonModesSlide.tsx:218` (`<h4>`) should become `<h3>`. Not required for AA, but it removes the h1→h3 jump the new heading creates on three slides.

## 1. HIGH — report viewer

### H1. No `<h1>` on slides ≥ 1 (VGC-259)
See §0. `TeamReport.tsx:280-391`. WCAG 1.3.1 / 2.4.6. Fix: `page.tsx:1141`, code above.

### H2. Mobile Pokémon-detail tab bar has no tab semantics and sub-44px targets
`PokemonDetailSlide.tsx:925-943` (bar) and `:945-950` (panels).
Four `<button>`s with no `role="tablist"`/`role="tab"`, no `aria-selected`, no `aria-controls`; the panels have no `role="tabpanel"`. Selected state is conveyed **only** by `bg-surface text-accent` (`:934-936`) — a colour-only state indicator. Height is `py-2` + `text-xs` ≈ 30 px.
WCAG **4.1.2 Name, Role, Value (A)**, **1.4.1 Use of Colour (A)**, 2.5.5 (project 44px standard).
Impact: this *is* the report on phones — Set / Stats / Notes / Calcs is the only way to reach three quarters of the content.
Fix: add `role="tablist"` to the container, `role="tab" aria-selected={mobileTab === tab} aria-controls={`panel-${tab}`} id={`tab-${tab}`}` to each button, `role="tabpanel" aria-labelledby={`tab-${tab}`}` + `tabIndex={0}` to the panel wrapper, arrow-key roving tabindex (mirror the pattern already written in `SlideNavControls.tsx:406-421`), and `min-h-[44px]`.

### H3. Generation theme swaps `--accent` to colours that fail 4.5:1 as text
`src/app/layout.tsx:101` (inline pre-hydration script) sets `--accent` per gen theme in **light** mode. Computed contrast of `text-accent` on `--surface #FFFFFF`:

| Theme | light `--accent` | ratio vs #FFF | verdict |
|---|---|---|---|
| gen9 (default) | `#e11d48` | 4.70 | pass (4.53 on `--background`, 4.28 on `--accent-surface` → **fails** in chips) |
| gen6 | `#dc2626` | 4.83 | pass |
| gen1 | `#8b5cf6` | 4.23 | **fail** |
| gen4 | `#3b82f6` | 3.68 | **fail** |
| gen7 | `#ea580c` | 3.56 | **fail** |
| gen3 | `#16a34a` | 3.30 | **fail** |
| gen2 | `#d97706` | 3.18 | **fail** |
| gen8 | `#0891b2` | ~3.1 | **fail** |
| gen5 | `#0ea5e9` | 2.81 | **fail** |

WCAG **1.4.3 Contrast (Minimum) (AA)**. `text-accent` is used for links, "View original", tab labels, the placement chip (`TeamOverview.tsx:441` `text-accent bg-accent-surface`, bold 12 px → needs 4.5, gets 4.28 even on the default theme), and dozens of other strings.
Honest limits: these are exact hex values against exact token backgrounds, so the numbers are reliable; what static analysis *cannot* rule out is a translucent overlay stacking behind the text somewhere.
Fix: keep the vivid hue for **fills/borders/icons** (needs only 3:1 under 1.4.11) and add a second token, e.g. `--accent-text`, darkened per theme to ≥ 4.5:1 on `#FFFFFF`/`#FAF9F6`/`#F2F0EB`, used by every `text-accent` utility. Dark-mode variants (`p.ad`) are light-on-dark and pass.

### H4. Any opacity modifier on `text-text-tertiary` drops text below AA
`--text-tertiary` is `#5E5E7A` (light) = 6.26:1 on white — fine at full strength. With Tailwind alpha it composites toward white and falls off fast: `/85` → 4.41, `/70` → 3.16, `/60` → 2.36, `/50` → 2.11, `/40` → 1.83, `/25` → 1.38. Dark mode behaves the same (`#9898B8` `/60` on `#0B0B1A` → 3.18).
Text occurrences (WCAG **1.4.3**):
* `DefensiveCoverageChart.tsx:196` `text-text-tertiary/25` — ~1.4:1, effectively invisible.
* `TournamentMode.tsx:52` `text-text-tertiary/40` for zero-value stats — 1.8:1; this is the tournament/OTS display surface.
* `PokemonDetailSlide.tsx:714` `/50` on the EV/SP total, `:686` `/70` on the nature label.
* `MatchupSheetRow.tsx:53` `/60` on row numbers.
* `SlideNavControls.tsx:536` `/70` on the "3/12" counter.
* `PasteInput.tsx:417` `placeholder:text-text-tertiary/40` — landing-page textarea placeholder is real text under 1.4.3.
Fix: delete the alpha and use the token directly, or introduce a `--text-quaternary` that is *itself* ≥ 4.5:1.
Non-text occurrences (WCAG **1.4.11 Non-text Contrast**, needs 3:1): `PokemonCard.tsx:278` and `:304` icon buttons at `text-text-tertiary/50` (2.1:1), `:322` MVP star at `/40` (1.8:1), `TeamStats.tsx:43/50/58/68` at `/60`. These are the calc/replace/MVP affordances on every card.

### H5. `<button>` nested inside `<a>` — invalid interactive nesting
* `src/components/explore/ReportCard.tsx:152` `<motion.a href=…>` wraps the like button (`:306`), the signed-out like button (`:320`) and the save button (`:336`), each neutralised with `e.stopPropagation()` (`:228`, `:249`, `:276`).
* `src/components/input/PasteInput.tsx:289` `<motion.a href="/champions">` wraps the dismiss `<button>` at `:312`.
Interactive content inside `<a>` is invalid HTML; browsers/AT recover inconsistently, and with a screen reader in browse mode the inner control is frequently unreachable or activates the link instead.
WCAG **4.1.2**, 1.3.1. Fix: make the card a `<div>` with a stretched-link `<a>` overlay (`::after` absolute inset) and move the buttons above it in z-order, or move the buttons outside the anchor.

## 5. Limits of this audit

Static only. I computed contrast from the literal token hexes in `globals.css` and the theme script in `layout.tsx` against the literal background utilities used at each call site — those numbers are exact. What I could **not** verify without a browser: composited translucency stacks (e.g. `bg-accent/8` over `bg-surface` over `--background`), text over the `bar-boosted`/`bar-speed-boosted` gradient stripes, focus-ring visibility against every background, real AT announcement order, and whether any `display:none`/`hidden` branch is actually pruned at the breakpoints in use. Touch-target figures are derived from Tailwind padding + font-size and assume the default 16 px root.
