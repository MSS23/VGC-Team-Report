### VGC-270 — TeamOverview gates both `<h1>` elements on `isReadOnly` → **CONFIRMED, and under-rated as Medium**

The diagnosis in the ticket is **accurate**. Exact current lines in `src/components/report/TeamOverview.tsx`:

| Line | Code | Guard |
|---|---|---|
| **418** | `{isReadOnly && !teamName && (` | sr-only fallback `<h1>` opens at **:419** |
| **424** | `{isReadOnly ? (` | the read-only/edit ternary the ticket calls "~:424" |
| **431** | `{teamName && (` | visible `<h1>` opens at **:432**, and it lives **inside** the `:424` read-only arm |

So the only two `<h1>` producers in the component are both unreachable when `isReadOnly === false`. The edit arm (`:528-656`) opens at `<h3>Team Details</h3>` (**:531**) and the team name is a bare `<input aria-label>` (**:538-546**). Slide 0 in edit mode renders **zero** `<h1>`.

Nothing compensates: `src/app/page.tsx:1153` gates its sr-only `<h1>` on `(tournamentMode || physicalSlide !== 0)`, and slide 0 is `physicalSlide === 0`. `layout.tsx`, `Navbar.tsx` and `PersistentNavbar.tsx` contain no `<h1>` (verified by grep across `src/**/*.tsx`).

**Severity correction — this is High, not "creator-only Medium".** `src/hooks/useHomePage.ts:526` defines `const isReadOnly = isSharedReadOnly || presentationMode || !creatorMode;` and `src/hooks/useCreatorMode.ts:6` is `useState(true)`. **`creatorMode` defaults to `true`**, so on the public homepage `/` the very first thing a visitor sees after pasting a team is an edit-mode slide 0 with no `<h1>`. It is not gated behind sign-in or a toggle. WCAG **1.3.1 (A)** / **2.4.6 (AA)**; also the SEO `<h1>` for `/`.

#### Double-`<h1>` risk analysis — what the fix must avoid

Today's read-only truth table for slide 0 (verified: `hasTournamentInfo` at **:381** is `!!(teamName || tournamentName || placement || record)`, so a truthy `teamName` always opens the `:425` block):

| `isReadOnly` | `teamName` | `:418` fires | `:431` fires | h1 count |
|---|---|---|---|---|
| true | falsy | ✅ | ❌ | **1** ✔ |
| true | truthy | ❌ | ✅ | **1** ✔ |
| false | falsy | ❌ | ❌ | **0** ✗ |
| false | truthy | ❌ | ❌ | **0** ✗ |

Ranked by how likely each wrong patch is:

1. **Highest risk — an unconditional `<h1 className="sr-only">` at the top of `TeamOverview` (i.e. deleting the whole `:418` guard).** This is the simplest-looking patch and it **doubles** the most common render in the product: read-only + `teamName` set → sr-only h1 at `:419` **and** visible h1 at `:432`. Every shared `/s/[id]` report with a team name would ship two `<h1>`s.
2. **High risk — promoting `<h3>Team Details</h3>` (`:531`) to `<h1>` while also relaxing `:418`.** Edit mode with no team name then yields two h1s (fallback + "Team Details"). "Team Details" is also a poor document title — it names a form section, not the page.
3. **High risk — relaxing the `physicalSlide !== 0` guard at `page.tsx:1153`.** That guard is the *only* thing keeping the host-level h1 off slide 0. Removing or loosening it doubles read-only slide 0 immediately. The guard is sound and should not be touched: `useSlideSystem.ts:124` gives `physicalSlide = visibleIndices[currentSlide]`, `page.tsx:1231` passes `currentSlide={physicalSlide}` to `TeamReport`, and `TeamReport.tsx:236` mounts `TeamOverview` only at `currentSlide === 0` — so `physicalSlide !== 0` ⟺ TeamOverview is not mounted, even under slide reorder/hide.
4. **Incomplete, not a double — changing `:418` to `{!teamName && …}`.** That fixes edit-mode-without-a-name but leaves **edit mode + team name set at zero h1**, because `:431` is inside the read-only arm. Half the bug survives.

**Recommended shape (exactly one h1 in all four cells, one-line diff, no new element in the edit tree):**

```tsx
{(!isReadOnly || !teamName) && (
  <h1 className="sr-only">
    {teamName || tournamentName || pokemon.map((e) => e.parsed.species).join(" / ") || "VGC Team Report"}
  </h1>
)}
```

Add `teamName ||` to the fallback text so edit mode announces the name the user is typing rather than the species list.

**Second-mount caveat the fixer must know:** `src/components/ui/PdfExport.tsx:90` mounts a **second** `TeamOverview` with `isReadOnly={true}` and — importantly — **never passes `teamName`**. So `:418`'s `!teamName` is always true there and the export always emits an h1. Today that is harmless (the container at `page.tsx:1757-1759` is `id="print-container"` + `aria-hidden="true"`, mounted only while `isPdfPrinting`, and `globals.css:653` hides everything else under `@media print`), but any patch that makes the h1 unconditional puts a second h1 in the DOM during export where axe/Lighthouse will count it. Two separate small bugs live here regardless: the print h1 falls back to the species list even when the report has a team name (missing prop), and `aria-hidden="true"` is applied to a subtree containing focusable controls.

**Verification the fixer should run:** on `/` (fresh paste, creator mode on) → exactly 1 h1; toggle creator mode off → exactly 1 h1; on `/s/<id>` with a team name → exactly 1 h1; on `/s/<id>` with no team name → exactly 1 h1; advance one slide in each → exactly 1 h1 (from `page.tsx:1154`).
