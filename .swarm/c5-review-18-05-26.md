## Regressions found

### CRITICAL: `INSERT INTO shares` column/value mismatch — new share creation broken
**File:** `src/app/api/share/route.ts` line 338–347

The column list has 8 columns:
```
(id, edit_token, data, version, is_public, owner_id, search_vector, species)
```
But the VALUES clause passes **9** positional arguments:
```
${id}, ${newEditToken}, ${JSON.stringify(state)}::jsonb, 1, ${isPublic ?? false},
${isUnlisted ?? false}, ${ownerId}, <search_vector>, <species>
```
Positions 5–7 map as: `is_public ← isPublic`, `owner_id ← isUnlisted` (a boolean!), `search_vector ← ownerId` (a string!). The `is_unlisted` column is never written.

**Effect:** Every new share created after this commit has `owner_id` set to `false` or `true` (boolean), which will cause all ownership checks (edit, visibility change, delete) to silently fail because `owner_id != userId`. The `is_unlisted` column also stays at its default (`false`), so unlisted shares are saved as private. This is a data-corruption regression — shares created after deploy are owned by nobody.

**Fix required:** Add `is_unlisted` to the column list:
```sql
INSERT INTO shares (id, edit_token, data, version, is_public, is_unlisted, owner_id, search_vector, species)
```

### Duplicate `extractSpecies` function — local copy diverges from shared utility
**File:** `src/app/api/share/route.ts` lines 47–67

A private `extractSpecies()` is defined locally in `share/route.ts`, but
`src/lib/utils/extract-species.ts` already exports a canonical version used by
`src/app/api/share/[id]/route.ts` and `src/app/api/user/reports/route.ts`. The
two implementations differ: the local one uses a line-by-line approach with
`startsWith` guards; the shared utility uses block-splitting on blank lines and
handles nicknames via a `(Name)` pattern. This means the `species[]` column
written on new/updated shares may not match what the read path reports, leading
to stale or mismatched species arrays.

**Fix:** Import from `@/lib/utils/extract-species` instead of the inline copy.

## Incomplete implementations

### Newsletter signup: no DB persistence, no double-opt-in
**File:** `src/app/api/newsletter/route.ts` lines 38–41

When `RESEND_API_KEY` is absent (all non-prod envs, initial prod deploy before key is set), the route returns `{ ok: true, method: "db" }` implying it saved to a database, but no DB insert happens. There is also no DB table fallback — signups are silently dropped.

Additionally, even with the Resend API key set, if `RESEND_AUDIENCE_ID` is missing the route does nothing (lines 65–68) but still returns `{ ok: true }`.

### `InstallPrompt` iOS branch: `timerFired` gate never used
**File:** `src/components/ui/InstallPrompt.tsx` lines 63–79

For the Android/Chrome path, `maybeReveal()` requires `timerFired && scrollFired && promptReady` all to be true before showing. For the iOS branch, the iosTimer only checks `scrollFired || pageIsShort` — the comment says "engagement gates" but `timerFired` is ignored, and `promptReady` (which is never set on iOS since no `beforeinstallprompt` fires) is also ignored. On iOS, the prompt will show after exactly 60s even with zero engagement if the page is short. This is intentional per the comment but contradicts the "both a 60-second dwell AND 200px scroll" contract in the code comments above.
